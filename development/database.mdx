Annie Mei uses [Diesel ORM](https://diesel.rs/) for migration management and [PostgreSQL](https://www.postgresql.org/) for data storage. The bot runs embedded migrations on startup and uses an `r2d2` connection pool for queries.

<Warning>
  As of v2.15.0, the bot has no Diesel-managed tables. The legacy `users` table was dropped in migration `2026-05-02-000001_drop_users_table` and `src/schema.rs` is empty. The bot reads OAuth-linked account data from the auth-service-owned `oauth_credentials` table using raw SQL (see `src/models/db/oauth_credential.rs`).
</Warning>

## Overview

Diesel provides:

- **Migration management** — Version-controlled schema changes
- **Connection pooling** — Reusable database connections via `r2d2`
- **Auto-generated schema** — Rust types from database tables (empty today)

<Warning>
  Never manually edit `src/schema.rs` — it's auto-generated by Diesel CLI.
</Warning>

## Configuration

Diesel is configured via `diesel.toml` at the project root:

```toml
[print_schema]
file = "src/schema.rs"

[migrations_directory]
dir = "migrations"
```

This tells Diesel:
- Where to write the generated schema (`src/schema.rs`)
- Where to find migration files (`migrations/` directory)

## Creating Migrations

Migrations are SQL files that modify the database schema. Each migration has two parts:

- `up.sql` — Apply changes
- `down.sql` — Revert changes

<Steps>
  <Step title="Generate Migration Files">
    Use the Diesel CLI to create migration scaffolding:

    ```bash
    diesel migration generate drop_legacy_table
    ```

    This creates a new directory:

    ```
    migrations/YYYY-MM-DD-HHMMSS_drop_legacy_table/
    ├── up.sql
    └── down.sql
    ```

    The timestamp prefix ensures migrations run in chronological order.
  </Step>

  <Step title="Write the Up Migration">
    Edit `up.sql` to define the change:

    ```sql migrations/YYYY-MM-DD-HHMMSS_drop_legacy_table/up.sql
    -- Drop the legacy bot-owned users table.
    -- After the OAuth /register flow shipped, the auth-service
    -- `oauth_credentials` table became the source of truth.
    DROP INDEX IF EXISTS users_discord_id_anilist_id_index;
    DROP TABLE IF EXISTS users;
    ```
  </Step>

  <Step title="Write the Down Migration">
    Edit `down.sql` to undo the change:

    ```sql migrations/YYYY-MM-DD-HHMMSS_drop_legacy_table/down.sql
    -- Recreate the legacy users table. Existing data cannot be restored
    -- from oauth_credentials (no anilist_username stored).
    CREATE TABLE users (
        discord_id bigint PRIMARY KEY,
        anilist_id bigint NOT NULL,
        anilist_username text NOT NULL
    );
    CREATE INDEX users_discord_id_anilist_id_index ON users (discord_id, anilist_id);
    ```

    <Info>
      The down migration should completely revert the up migration, allowing you to roll back if needed.
    </Info>
  </Step>

  <Step title="Run the Migration">
    Apply the migration to your database:

    ```bash
    diesel migration run
    ```

    This:
    1. Executes the SQL in `up.sql`
    2. Updates `src/schema.rs` (empty today)
    3. Records the migration in the `__diesel_schema_migrations` table
  </Step>
</Steps>

## Rolling Back Migrations

Revert the most recent migration:

```bash
diesel migration revert
```

Revert all migrations:

```bash
diesel migration revert --all
```

## Querying with Raw SQL

Since the bot has no Diesel-managed tables, queries use `diesel::sql_query` against the auth-service-owned `oauth_credentials` table:

```rust src/models/db/oauth_credential.rs
use diesel::prelude::*;
use diesel::sql_types::Text;
use serenity::model::prelude::UserId;

#[derive(QueryableByName, Debug, Clone)]
#[diesel(check_for_backend(diesel::pg::Pg))]
pub struct OAuthCredential {
    #[diesel(sql_type = Text)]
    pub discord_user_id: String,
    #[diesel(sql_type = Text)]
    pub anilist_id: i64,
}

impl OAuthCredential {
    pub fn get_by_discord_id(
        discord_id: UserId,
        conn: &mut PgConnection,
    ) -> Result<Option<Self>, diesel::result::Error> {
        diesel::sql_query(
            "SELECT discord_user_id, anilist_id FROM oauth_credentials WHERE discord_user_id = $1"
        )
        .bind::<Text, _>(discord_id.get().to_string())
        .get_result(conn)
        .optional()
    }
}
```

Key points:

- `QueryableByName` — Maps query results to struct fields by column name
- `sql_query` — Executes raw SQL with Diesel's connection management
- `optional()` — Returns `Ok(None)` when no row matches instead of an error

## Database Connection

The connection pool lives in `src/utils/database.rs`:

```rust
use diesel::prelude::*;
use diesel::pg::PgConnection;
use diesel::r2d2::{ConnectionManager, Pool, PooledConnection};
use std::env;

pub type DbPool = Pool<ConnectionManager<PgConnection>>;
pub type DbConnection = PooledConnection<ConnectionManager<PgConnection>>;

pub fn create_pool() -> DbPool {
    let database_url = env::var("DATABASE_URL")
        .expect("DATABASE_URL must be set");

    let manager = ConnectionManager::<PgConnection>::new(database_url);
    Pool::builder()
        .build(manager)
        .expect("Error creating database pool")
}

pub fn get_connection(pool: &DbPool) -> DbConnection {
    pool.get().expect("Error retrieving pooled database connection")
}
```

The bot creates the pool and runs migrations at startup in `src/main.rs`:

```rust
let database_pool = create_pool();
let connection = &mut get_connection(&database_pool);
run_migration(connection);
```

## Running Migrations Programmatically

Annie Mei runs migrations automatically at startup using `diesel_migrations`:

```rust src/utils/database.rs
use diesel_migrations::{embed_migrations, EmbeddedMigrations, MigrationHarness};
use diesel::pg::PgConnection;

pub const MIGRATIONS: EmbeddedMigrations = embed_migrations!();

pub fn run_migration(conn: &mut PgConnection) {
    conn
        .run_pending_migrations(MIGRATIONS)
        .expect("Failed to run migrations");
}
```

This ensures the database schema is always up-to-date when the bot starts.

## Migration Best Practices

<CardGroup cols={2}>
  <Card title="Always Write Down Migrations" icon="arrow-rotate-left">
    Every `up.sql` must have a corresponding `down.sql` that fully reverts the changes.
  </Card>

  <Card title="Test Migrations" icon="flask">
    Test both up and down migrations:

    ```bash
    diesel migration run
    diesel migration revert
    diesel migration run
    ```
  </Card>

  <Card title="Use Transactions" icon="arrows-rotate">
    Wrap complex migrations in transactions:

    ```sql
    BEGIN;
    -- Multiple statements here
    COMMIT;
    ```
  </Card>

  <Card title="Avoid Data Loss" icon="triangle-exclamation">
    Be cautious with dropping tables or removing columns. Document what cannot be restored in the down migration comment.
  </Card>
</CardGroup>

## Troubleshooting

<AccordionGroup>
  <Accordion title="Schema.rs not updating">
    Manually regenerate the schema:

    ```bash
    diesel print-schema > src/schema.rs
    ```

    Or delete `src/schema.rs` and re-run migrations.
  </Accordion>

  <Accordion title="Migration order is wrong">
    Diesel runs migrations in timestamp order. If you need to reorder:

    1. Revert all migrations: `diesel migration revert --all`
    2. Rename migration directories to change timestamps
    3. Re-run migrations: `diesel migration run`
  </Accordion>

  <Accordion title="Can't connect to database">
    Verify environment variables:

    ```bash
    echo $DATABASE_URL
    ```

    Test connection:

    ```bash
    psql $DATABASE_URL -c "SELECT 1"
    ```
  </Accordion>
</AccordionGroup>
