Annie Mei uses [SQLx](https://github.com/launchbadge/sqlx) for PostgreSQL database access and [PostgreSQL](https://www.postgresql.org/) for data storage. The bot uses an async connection pool for queries.

<Warning>
  As of v2.15.0, the bot has no bot-owned tables. The legacy `users` table was dropped in migration `2026-05-02-000001_drop_users_table`. The bot reads OAuth-linked account data from the auth-service-owned `oauth_credentials` table using `sqlx::query_as` (see `src/models/db/oauth_credential.rs`).
</Warning>

## Overview

SQLx provides:

- **Async queries** — Non-blocking database access compatible with the Tokio runtime
- **Compile-time query checking** — Optional `query!` macro that verifies SQL at build time
- **Connection pooling** — Reusable database connections via `sqlx::PgPoolOptions`
- **Type-safe models** — `#[derive(FromRow)]` for mapping query results to Rust structs

## Configuration

The database connection pool is configured in `src/utils/database.rs`:

```rust
use sqlx::{Pool, Postgres, postgres::PgPoolOptions};
use std::time::Duration;

pub async fn create_pool() -> DbPool {
    let database_url = env::var(DATABASE_URL).expect("DATABASE_URL must be set");

    PgPoolOptions::new()
        .max_connections(10)
        .min_connections(0)
        .max_lifetime(Duration::from_secs(20 * 60))
        .idle_timeout(Duration::from_secs(60))
        .test_before_acquire(true)
        .connect(&database_url)
        .await
        .expect("Error creating database pool")
}
```

### Connection pool settings

| Setting | Value | Purpose |
|---------|-------|---------|
| `max_connections` | 10 | Maximum concurrent connections |
| `min_connections` | 0 | Minimum idle connections |
| `max_lifetime` | 20 minutes | Connection recycling interval |
| `idle_timeout` | 60 seconds | Idle connection cleanup |
| `test_before_acquire` | true | Validate connections before use |

## Migrations

Annie Mei uses SQLx migrations stored in `migrations/`. Each migration has `up.sql` and `down.sql` files in timestamped directories.

<Note>
  The migration directory contains historical migrations from when the bot used Diesel. Since the bot no longer has bot-owned tables (the `users` table was dropped), you typically only need to run migrations if you're also managing the auth service database. The bot itself connects to an existing database with the expected schema already in place.
</Note>

### Current migration history

```
migrations/
├── 00000000000000_diesel_initial_setup/
├── 2023-01-22-200806_create_users/
├── 2023-02-02-075156_remove_unique_constraint_from_user/
├── 2023-02-02-080943_users_add_index_discord_id_anilist_id/
└── 2026-05-02-000001_drop_users_table/
```

### Creating migrations

Use the SQLx CLI to create migration scaffolding:

```bash
sqlx migrate add <migration_name>
```

This creates a new directory:

```
migrations/YYYYMMDDHHMMSS_<migration_name>/
├── up.sql
└── down.sql
```

<Note>
  The existing migrations use the legacy Diesel timestamp format (`YYYY-MM-DD-HHMMSS_name`). New migrations created with `sqlx migrate add` use the SQLx format (`YYYYMMDDHHMMSS_name`). Both formats work with SQLx CLI.
</Note>

### Running migrations

**Manually during development**:

```bash
sqlx migrate run
```

**Reverting** (requires manual reversion):

```bash
sqlx migrate revert
```

## Querying with SQLx

The bot reads from the auth-service-owned `oauth_credentials` table using `sqlx::query_as` with `FromRow` structs:

```rust src/models/db/oauth_credential.rs
#[derive(Clone, PartialEq, Eq, FromRow)]
pub struct OAuthCredential {
    pub discord_user_id: String,
    pub anilist_id: i64,
    pub anilist_username: Option<String>,
}

impl OAuthCredential {
    pub async fn get_by_discord_id(
        user_discord_id: UserId,
        pool: &DbPool,
    ) -> Result<Option<OAuthCredential>, sqlx::Error> {
        sqlx::query_as::<_, OAuthCredential>(
            "SELECT discord_user_id, anilist_id, anilist_username \
             FROM oauth_credentials WHERE discord_user_id = $1"
        )
        .bind(user_discord_id.get().to_string())
        .fetch_optional(pool)
        .await
    }
}
```

Key points:

- **`FromRow`** — Derives `sqlx::FromRow` to map query columns to struct fields by name
- **`query_as`** — Executes raw SQL and maps results to a typed struct
- **`fetch_optional`** — Returns `Ok(None)` when no row matches instead of an error
- **Async** — All queries are `async` and compatible with the Tokio runtime
- **Pool reference** — Pass `&DbPool` rather than acquiring a connection manually

### Batch lookups

The `get_by_discord_ids` method queries multiple users at once for guild member status:

```rust
pub async fn get_by_discord_ids(
    user_discord_ids: Vec<UserId>,
    pool: &DbPool,
) -> Result<Vec<OAuthCredential>, sqlx::Error> {
    let ids: Vec<String> = user_discord_ids.iter().map(|id| id.get().to_string()).collect();

    sqlx::query_as::<_, OAuthCredential>(
        "SELECT discord_user_id, anilist_id, anilist_username \
         FROM oauth_credentials WHERE discord_user_id = ANY($1)"
    )
    .bind(ids)
    .fetch_all(pool)
    .await
}
```

## Writing data

The `/unregister` command demonstrates writing data using SQLx transactions:

```rust
async fn delete_user_registration_in_transaction(
    discord_id: u64,
    conn: &mut PgConnection,
) -> Result<DeletedRegistrations, sqlx::Error> {
    let oauth_credentials_deleted = sqlx::query(
        "DELETE FROM oauth_credentials WHERE discord_user_id = $1"
    )
    .bind(discord_id.to_string())
    .execute(conn)
    .await?
    .rows_affected();

    let oauth_sessions_deleted = sqlx::query(
        "DELETE FROM oauth_sessions WHERE discord_user_id = $1"
    )
    .bind(discord_id.to_string())
    .execute(conn)
    .await?
    .rows_affected();

    Ok(DeletedRegistrations { oauth_credentials_deleted, oauth_sessions_deleted })
}
```

Transactions are started from the pool:

```rust
let mut transaction = pool.begin().await?;
// ... execute statements ...
transaction.commit().await?;
```

## Accessing the pool in commands

The connection pool is stored in Serenity's `TypeMap` and accessed in command handlers:

```rust
use crate::utils::database::DatabasePoolKey;

let Some(database_pool) = get_pool_from_context(ctx).await else {
    // Handle missing pool
    return;
};
```

## Setup

### Install SQLx CLI

```bash
cargo install sqlx-cli --no-default-features --features postgres
```

### Create the database

```bash
createdb annie_mei
```

Or using psql:

```sql
CREATE DATABASE annie_mei;
```

### Run migrations manually

```bash
sqlx migrate run
```

### Check migration status

```bash
sqlx migrate info
```

## Troubleshooting

<AccordionGroup>
  <Accordion title="Can't connect to database">
    Verify environment variables:

    ```bash
    echo $DATABASE_URL
    ```

    Test connection:

    ```bash
    psql $DATABASE_URL -c "SELECT 1"
    ```
  </Accordion>

  <Accordion title="Migration failures">
    Check the current migration state:

    ```bash
    sqlx migrate info
    ```

    For persistent issues, inspect the `_sqlx_migrations` table directly.
  </Accordion>

  <Accordion title="Pool exhaustion">
    If you see connection timeout errors:

    - Check `max_connections` in `create_pool()` (default: 10)
    - Ensure PostgreSQL's `max_connections` is higher than the pool limit
    - Look for long-running queries or missing `await` points
  </Accordion>
</AccordionGroup>
